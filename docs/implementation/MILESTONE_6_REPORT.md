# Milestone 6 Report: ADR-011 Implementation & Patient Registration Unblocking

## Overview
This report documents the implementation of the accepted architectural decision (ADR-011) for Medical Record Number (MRN) generation and the subsequent unblocking of the Patient Registration flow.

## Implementation Details

### 1. Database Sequence
- **Mechanism**: PostgreSQL SEQUENCE
- **Sequence Name**: `patient_mrn_seq_2026`
- **Migration**: `apps/backend/src/db/migrations/0002_mrn_sequence.sql`
- **Format**: `MRN-YYYY-NNNNN` (where `YYYY` is dynamically evaluated at runtime, and `NNNNN` is a 5-digit zero-padded sequence).

### 2. Constraints and Atomicity
- **Uniqueness**: Enforced securely at the database level by the existing `mrn VARCHAR(20) NOT NULL UNIQUE` constraint on the `patients` table.
- **Rollback Behavior (Gap Policy)**: As defined in ADR-011, sequence generation is intentionally non-transactional. If a transaction fails (e.g. unique constraint violation, audit write failure), the fetched sequence value is permanently consumed, creating an acceptable gap in the MRN numbering.
- **Audit Atomicity**: The patient insertion and the corresponding `PATIENT_REGISTERED` audit event are executed strictly within the *same* database transaction. If the audit log fails (e.g., due to tamper-prevention locks or hash chain issues), the entire patient creation is rolled back.

### 3. Concurrency Safety
The use of PostgreSQL's native `nextval()` function guarantees that simultaneous requests for MRNs yield unique numbers instantaneously, completely sidestepping application-level deadlocks or serialization bottlenecks that would otherwise occur if locking tables were used.

### 4. RBAC and Authorization
- The backend relies strictly on the `M5` authoritative RBAC boundary. The frontend is exclusively responsible for UX visibility.
- M4 (Authentication) validates tokens and populates the authenticated principal (including `staffId` and `departmentId`). No simulated or fake "system" users are employed.
- Authorization endpoints correctly demand `patient:create` and `patient:read` access.

### 5. Patient Search
Trigram fuzzy search on patient names via `pg_trgm` was verified to function flawlessly alongside MRN queries.

### 6. Frontend State
The `Patient UI` (Registration Page) has been cleared of the `NotImplementedError` mock-blocker. Submitting the registration form now successfully transacts with the backend, producing the valid `MRN-YYYY-NNNNN` generated by the PostgreSQL sequence and displaying the patient profile.

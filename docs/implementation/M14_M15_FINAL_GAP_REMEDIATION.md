## Gap 2 — Audit Vocabulary

### Architecture

Per `docs/architecture/security-architecture.md` §2.5 and
`docs/architecture/api-architecture.md` line 305, the canonical audit
event vocabulary for break-glass is:

* `BREAK_GLASS_ACTIVATED` — session created
* `BREAK_GLASS_RECORD_ACCESSED` — record accessed under session (per M7)
* `BREAK_GLASS_DEACTIVATED` — session forcibly ended (manual revoke)
* `BREAK_GLASS_REVIEWED` — post-activation review by Security Admin
  (semantically distinct from deactivation; review does not terminate the
  session)

### Implementation (After This Remediation)

Aligned to the architecture:

* `apps/backend/src/modules/break-glass/break-glass.service.ts:209` —
  `eventType: 'BREAK_GLASS_DEACTIVATED'` (was `'BREAK_GLASS_REVOKED'`).
* `apps/backend/src/modules/break-glass/__tests__/break-glass.verification.test.ts`:
  - 9e. `BREAK_GLASS_DEACTIVATED` audit event emitted (renamed from
    "REVOKED").
  - 9f. Historical compatibility: prior `BREAK_GLASS_REVOKED` events from
    older runs are not mutated (asserted explicitly).
* `BREAK_GLASS_ACTIVATED` and `BREAK_GLASS_REVIEWED` are unchanged.

### Historical Data

The audit log is immutable. Existing rows with the prior
`BREAK_GLASS_REVOKED` eventType value are preserved as-is; the hash chain
(`previousHash` → `recordHash`) is intact. The new `9f` test asserts that:

* The current revocation emits the canonical `BREAK_GLASS_DEACTIVATED`.
* No new rows in the test's session target carry the obsolete
  `BREAK_GLASS_REVOKED` eventType.

This is the standard canonical-vocabulary-alignment pattern: only forward-
written events use the new name; historical rows keep their original value
to preserve forensic chain-of-custody.

### Compatibility

* API contract: the audit event types are internal domain vocabulary
  (not exposed in any external API response). The `break-glass/sessions`
  endpoints return session state, not audit event names. No API consumer
  is affected.
* `api-architecture.md` line 305: now matches the implementation.
* `security-architecture.md` §2.5: matches.
* `M6_M13_AUDIT_REPORT.md`: the prior "known documented deviation" is
  resolved.

### Audit Hash Chain

`audit_events` schema is unchanged (`eventType` is `varchar(100)`). No
schema migration is required. The `recordHash` continues to be computed
from a canonical serialization that includes `eventType`, so:

* New events: `recordHash = sha256(previousHash + canonical({...,eventType: 'BREAK_GLASS_DEACTIVATED',...}))`.
* Old events: `recordHash = sha256(previousHash + canonical({...,eventType: 'BREAK_GLASS_REVOKED',...}))`.

Each row's stored `recordHash` matches its stored payload byte-for-byte.
The full audit integrity suite
(`apps/backend/src/modules/audit/__tests__/audit.integrity.test.ts`) was
re-run and passed (4/4 tests).

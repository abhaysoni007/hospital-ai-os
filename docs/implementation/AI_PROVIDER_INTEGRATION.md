# AI Provider Integration (ADR-017 & ADR-020)

## Overview
The Hospital AI OS M12 pipeline orchestrates AI generations strictly through a centralized provider abstraction (`AIProviderAdapter`). This documentation details the supported providers, their configuration, and the strict invariants enforced.

## Supported Providers

### 1. Google Gemini (Default)
The original provider implemented in M11. 
- Adapter: `GeminiAdapter`
- Provider Code: `google-gemini`

### 2. OpenAI-Compatible (ChatModel / Nemotron)
Added in M12 to support standardized Chat Completion endpoints, specifically targeting NVIDIA NIM / Nemotron 3.5 Lightning.
- Adapter: `OpenAICompatibleAdapter`
- Provider Code: `openai-compatible`
- Required properties: `AI_BASE_URL`, `AI_MODEL`, `AI_API_KEY`

### 3. Fake Provider
Used exclusively for tests to ensure deterministic output and no actual network calls.
- Adapter: `FakeProvider`
- Provider Code: `fake`

## Configuration

To configure the OpenAI-compatible provider (e.g. NVIDIA NIM), set the following environment variables (defined in `.env`):

```bash
AI_ENABLED=true
AI_PROVIDER=openai-compatible
AI_API_KEY=<YOUR_API_KEY>
AI_BASE_URL=https://integrate.api.nvidia.com/v1
AI_MODEL=nvidia/nemotron-3.5-lightning-30b-a3b
```

### Readiness Rules
- **Disabled/Fail-Closed**: If `AI_ENABLED` is false, or if `AI_PROVIDER` is set but credentials/base URL are missing, the system boots with AI disabled.
- For `openai-compatible`, **BOTH** `AI_API_KEY` and `AI_BASE_URL` must be present.
- Production requires `ENCRYPTION_KEY` to be at least 32 characters, otherwise AI is disabled.

## Wire Contract & Invariants (M12.1)

The M12.1 Canonical Wire Invariant dictates that the `userPrompt` generated by the orchestrator (which includes the strictly formatted context blocks) MUST be transmitted exactly as-is.

- **No Serialization**: The adapter NEVER performs `JSON.stringify(params.context)`. The `context` array is only used by the orchestrator for metadata tracking, manifest creation, and gaps detection.
- **No Prompt Modification**: The adapter MUST NOT prepend, append, or modify the `systemInstruction` or `userPrompt`.
- **Structured Output**: The adapter uses `response_format: { type: 'json_object' }` if the backend supports it. Regardless, the string payload returned by the provider is passed entirely back into the existing validation pipeline (`runValidationPipeline`). The adapter does not attempt to repair or weaken validation logic.

## Error Mapping
Provider errors are mapped to the standard `AIProviderError` taxonomy to ensure consistent resilience logic (e.g. circuit breaking):
- `401 / 403`: Mapped to `UNAVAILABLE` (Configuration/auth failures).
- `429`: Mapped to `RATE_LIMITED`.
- `408 / Timed Out`: Mapped to `TIMEOUT`.
- `5xx / Fetch Failed`: Mapped to `UNAVAILABLE`.
- Malformed Output: Passed as raw string and handled by the M12 `runValidationPipeline` which will emit `validation_failed`.

## Security Rules
1. The API Key MUST NOT be committed, logged, or exposed in error messages.
2. The authorization header and raw provider request are never logged in plaintext.
3. The raw provider response is stored securely via `encryptField` and never in plaintext, ensuring any clinical data is protected at rest.

## Local Manual Setup
For local testing of the NVIDIA Nemotron integration using PowerShell:

```powershell
$env:AI_ENABLED="true"
$env:AI_PROVIDER="openai-compatible"
$env:AI_API_KEY="<PASTE_YOUR_NVIDIA_KEY_HERE>"
$env:AI_BASE_URL="https://integrate.api.nvidia.com/v1"
$env:AI_MODEL="nvidia/nemotron-3.5-lightning-30b-a3b"
```
*(Do NOT paste your key into `.env.example` or any source code files!)*
